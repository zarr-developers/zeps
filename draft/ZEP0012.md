# ZEP 12 — Explicit array bounds

Authors:

- [Jeff Rhoades](https://github.com/rhoadesScholar), E11 Bio

Status: Draft

Type: Specification

Created: 2026-10-19

Discussion: <https://github.com/zarr-developers/zarr-specs/pull/400>

## Abstract

A Zarr v3 array occupies the coordinates `[0, shape)` along each dimension, and the regular chunk
grid is anchored at coordinate 0. Together these make growing an array before its first element the
one resize that cannot be done by editing metadata: every existing chunk has to move to a new key,
or be copied. This ZEP adds `bounds` to the array metadata as an alternative to `shape`, giving each
dimension an explicit half-open coordinate range, and lets the regular chunk grid's indices be
negative. Adding `n` elements in front becomes a change to one number in `zarr.json`; existing
chunks keep their keys and existing elements keep their coordinates. Arrays written with `shape`
are unchanged. A reader that does not implement this ZEP refuses an array that uses it, on two
independent grounds: `bounds` is a member it does not recognise, and `shape` is absent.

## Motivation and Scope

Volumes that are assembled over time rarely arrive in index order. Serial-section imaging adds
sections at either end of a stack; a tiled acquisition is registered as tiles land, and the first
tile is not the one at the corner; a time series gets a backfill. In every case the existing data
should keep its coordinates, because other arrays, annotations and viewers already refer to them,
and the new data goes in front.

Zarr v3 cannot express that. Coordinates run from 0 and the regular chunk grid is aligned at 0, so
the only way to add `n` elements before the first is to grow `shape` and shift everything else by
`n`: every chunk is read and written under a new key (or renamed, on a filesystem), and every
coordinate held outside the array is off by `n`. The cost grows with the number of chunks, and on
an object store each move is a copy and a delete. The regular grid specification names the need: it
notes that "extensions may define variations on the regular grid type such that the grid indices
may include negative integers, and the origin element of the array may occur at an arbitrary
position within any chunk, which is required to allow arrays to be extended by an arbitrary length
in a 'negative' direction along any dimension."

A chunk grid extension can do it, and the first draft of
[zarr-extensions#81](https://github.com/zarr-developers/zarr-extensions/pull/81) prototyped one,
but the discussion in
[zarr-extensions#79](https://github.com/zarr-developers/zarr-extensions/issues/79) converged on a
core change instead. A chunk grid's job is to map coordinates to chunks; where the coordinates
start is a property of the array. A metadata-only reader, one that reports the extent of an array
from `shape` and `data_type` without consulting the chunk grid, would silently report the wrong
extent if the lower bound lived inside `chunk_grid`. Putting the bounds where `shape` is means a
reader either understands them or refuses the array.

In scope:

- a `bounds` member of the array metadata, as an alternative to `shape`;
- negative chunk grid indices on the `regular` chunk grid, and a first chunk that may overhang the
  array as the last one already may;
- how the `default` and `v2` chunk key encodings write a negative index.

Out of scope: placing chunk grid index 0 at a coordinate other than 0, which the `offset` chunk
grid proposed in zarr-extensions#81 provides for any grid, `rectilinear` included (see
Implementation); dimensions of infinite or unknown extent; how implementations expose array
indices to their users.

## Usage and Impact

What users see is up to each implementation's array API. zarr-python's prototype keeps zero-based
indexing, so `a[0]` is the first element before and after a prepend, and reports the coordinate
range as a separate property:

```python
import numpy as np
import zarr

a = zarr.create_array(store, shape=(6, 4), chunks=(4, 2), dtype="int32")
a[:] = np.arange(24).reshape(6, 4)       # chunks c/0/0, c/0/1, c/1/0, c/1/1

a.prepend(np.full((3, 4), -1), axis=0)   # one zarr.json write, then the new chunks
a.shape    # (9, 4)
a.domain   # ((-3, 6), (0, 4))
a[3:]      # the original data; its chunks were not touched
```

The metadata after the prepend:

```json
{
  "bounds": {"inclusive_min": [-3, 0], "exclusive_max": [6, 4]},
  "chunk_grid": {"name": "regular", "configuration": {"chunk_shape": [4, 2]}}
}
```

The three new rows fill the rest of chunk `-1` along the first dimension, stored under `c/-1/0`
and `c/-1/1`. Nothing else in the store changes.

The same growth today, for an array on a filesystem store, is a `resize` followed by a move of
every chunk to its new key:

```python
n0, n1 = a.cdata_shape
a.resize((a.shape[0] + k * a.chunks[0],) + a.shape[1:])
for i in reversed(range(n0)):
    for j in range(n1):
        os.rename(root / "c" / str(i) / str(j), root / "c" / str(i + k) / str(j))
```

Measured with 64³ `uint8` chunks (256 KiB each), growing by two chunk rows, the metadata step
against the three ways available today:

| chunks | rename (filesystem) | copy + delete per chunk | copy the array | metadata write |
|-------:|--------------------:|------------------------:|---------------:|---------------:|
|  4 096 |              0.13 s |                   5.9 s |          3.1 s |        0.002 s |
| 32 768 |               1.0 s |                    44 s |           26 s |        0.002 s |

Every column was run on one machine's NVMe filesystem through zarr-python 3.4.1's store API; no
object store was measured. The copy columns are the operations an object store would need, since it
cannot rename. The measurement used the first draft of zarr-extensions#81, a chunk grid prototype
of this design; under this ZEP the metadata step is the same single write of `zarr.json`. Writing
the new data costs the same in every column and is not included. The first three columns grow with
the array; the last does not.

## Backward Compatibility

Arrays written with `shape` are unaffected: their metadata is unchanged and means what it meant,
and an implementation of this ZEP treats them exactly as before.

An array that uses `bounds` has no `shape`. A reader that does not implement this ZEP refuses it
twice over. A reader that follows the core specification fails to open an array whose metadata has
a member it does not recognise, and `bounds` is such a member. A reader that ignores unknown
members instead, which neuroglancer does today, refuses the array because `shape` is missing. The
guarantee does not depend on either behaviour alone.

That is why `bounds` replaces `shape` instead of sitting beside it, and why a chunk grid origin
belongs under a grid name of its own rather than in the `regular` configuration (see
Alternatives). The alternatives were checked against current readers, and some open the array and
address every chunk from 0:

| metadata | zarr-python | tensorstore | neuroglancer |
|---|---|---|---|
| a new member inside the `regular` configuration, with `shape` | opens, ignores it | refuses | opens, ignores it |
| an unknown top-level member next to `shape` | refuses | refuses | opens, ignores it |
| `shape` absent | refuses | refuses | refuses |

(zarr-python and neuroglancer from their main branches in October 2026, tensorstore 0.1.85. Other
implementations were not checked.)

Any array converts between the two forms without touching a chunk: `shape` becomes `bounds` with
`inclusive_min` all zeros and `exclusive_max` equal to `shape`, and back when every entry of
`inclusive_min` is 0. A writer choosing a form SHOULD write `shape` whenever every lower bound is 0,
so that arrays which do not need this feature stay readable everywhere, and SHOULD keep whichever
form a stored document has when it updates the array, unless the new extent no longer starts at 0.
Because an array's first prepend makes it unreadable by readers that predate this ZEP, an
implementation SHOULD make that step an explicit choice rather than a side effect.

This is a minor version of the core specification, 3.2, under its stability policy: a 3.1 reader
fails to open an array using `bounds` because the member is unknown to it, which is the policy's own
example of an additive feature, and data not using `bounds` is readable by both. The regular chunk
grid and the `default` and `v2` chunk key encodings each move to version 1.1.

## Detailed description

### `bounds`

An array metadata document MUST contain exactly one of `shape` and `bounds`.

`bounds` is an object with two members, `inclusive_min` and `exclusive_max`, each an array of
integers with one entry per dimension. The two arrays MUST have the same length, and
`inclusive_min[i] <= exclusive_max[i]` for every dimension `i`. Below, `start` and `stop` denote
`inclusive_min[i]` and `exclusive_max[i]`. The elements of the array along dimension `i` have the
coordinates `start, start + 1, ..., stop - 1`; a dimension with `start == stop` has length 0. A
zero-dimensional array has `"bounds": {"inclusive_min": [], "exclusive_max": []}`.

The entries of `inclusive_min` and `exclusive_max` MUST be representable as signed 64-bit integers,
and MUST be chosen so that the length of every dimension is as well.

The number of dimensions is the length of `inclusive_min`, and the shape is derived: the length
of dimension `i` is `stop - start`. `shape` keeps its meaning and is equivalent to `bounds` with
every entry of `inclusive_min` 0 and `exclusive_max` equal to `shape`. Wherever the
specification refers to the shape or to the length of a dimension, the derived value applies;
`dimension_names`, if present, has one entry per dimension.

### Negative grid indices on the regular chunk grid

The `regular` chunk grid keeps its form: the configuration has the single member `chunk_shape`,
and chunk grid index 0 begins at coordinate 0 along every dimension. What changes is the range of
the grid. Along a dimension with chunk length `d`, chunk grid index `g` covers the coordinates
`[g * d, (g + 1) * d)`. The element at coordinate `x` is in the chunk with grid index
`floor(x / d)`, at position `x mod d` within it, with floor division and the modulo that pairs
with it so that both are defined for `x < 0`. Grid indices MAY be negative.

Along a dimension with bounds `[start, stop)` the grid runs from grid index `floor(start / d)`
through `floor((stop - 1) / d)` when `stop > start`, and has no chunks otherwise. The first chunk
MAY contain positions below `start`, exactly as the last chunk may contain positions at or above
`stop`: those positions are not elements of the array, and a writer SHOULD store the fill value
there. Every chunk is encoded at the full `chunk_shape`.

Nothing more is needed to prepend: the chunk holding the first element is `floor(start / d)`, and
with `start` 0 it is chunk 0, as today. Placing chunk 0 elsewhere, which
[@jbms](https://github.com/jbms) asked for on zarr-extensions#79 so that chunk boundaries can be
aligned with another array's or with a source's, is left to a wrapper chunk grid:
zarr-extensions#81 proposes `offset`, whose configuration holds an `offset` and a
`base_chunk_grid`, so that any registered grid gains a non-zero origin without a member of its own
(see Alternatives). Earlier drafts of this ZEP carried an `origin` member on `regular` instead.

The sharding codec is unaffected. A shard is a chunk of the outer grid and is positioned by the same
rule as any chunk, so a shard grid index may be negative; its inner chunks are positioned relative
to the shard, so their indices within it are unchanged. An inner chunk that lies wholly outside the
bounds is marked empty in the shard index, as any unwritten inner chunk is; the index always covers
every inner chunk of the shard. Where the sharding specification says "array shape", the derived
shape and the bounds apply, as for the core specification.

### Growing and shrinking

To add `n` elements before the first along dimension `i`, a writer sets `inclusive_min[i] -= n`.
The grid index of every existing chunk is unchanged, so no chunk changes key. The new
elements occupy the rest of what was the first chunk and, when `n` is large enough, chunks at lower
grid indices. Growing after the last element is `exclusive_max[i] += n`, as `shape[i] += n` is today,
and shrinking from either end is the matching decrease. The specification's note on resizing
applies at both ends: chunks that already exist in the region being grown into are shown unless
the writer clears them.

### Negative chunk indices in chunk keys

The `default` and `v2` chunk key encodings write each grid index as its ASCII decimal string; a
negative index carries a leading `-`, as in `c/-1/0`. The string `-0` MUST NOT be written and MUST
be rejected when a key is parsed. Negative components do not sort numerically under the
lexicographic order of keys (`c/-2` sorts after `c/-1`), which an implementation that lists keys by
range has to allow for. Only an array that uses `bounds` can produce a negative grid index, so an
implementation that indexes chunks with unsigned integers needs a signed index on that path alone.

### Example

```json
{
  "zarr_format": 3,
  "node_type": "array",
  "bounds": {"inclusive_min": [-3, -2], "exclusive_max": [6, 7]},
  "data_type": "uint16",
  "chunk_grid": {
    "name": "regular",
    "configuration": {"chunk_shape": [4, 5]}
  },
  "chunk_key_encoding": {"name": "default"},
  "codecs": [{"name": "bytes", "configuration": {"endian": "little"}}],
  "fill_value": 0
}
```

A 6 by 7 array with 4 by 5 chunks, grown by 3 rows and 2 columns in front. Its elements occupy
`[-3, 6) x [-2, 7)` and the grid indices run `-1, 0, 1` along both dimensions. The first element is
at position 1 of chunk `-1` along the first dimension and position 3 of chunk `-1` along the second.
The original four chunks keep their keys `c/0/0`, `c/0/1`, `c/1/0` and `c/1/1`; the new ones are
`c/-1/-1`, `c/-1/0`, `c/-1/1`, `c/0/-1` and `c/1/-1`.

## Related Work

- [tensorstore](https://google.github.io/tensorstore/) gives every array an index domain with an
  inclusive lower and exclusive upper bound per dimension (`inclusive_min` and `exclusive_max` in
  its JSON), either of which may be implicit so that
  a resize can move it. The
  [neuroglancer precomputed format](https://github.com/google/neuroglancer/blob/master/src/datasource/precomputed/volume.md)
  stores a `voxel_offset` beside each scale's `size`. Both are coordinate ranges that need not start
  at 0, over a chunk grid whose alignment is independent of the lower bound.
- [Icechunk](https://icechunk.io/)'s `shift_array` moves chunk references by whole chunks inside its
  versioned store. It does not change the plain Zarr representation and works in chunk units.
- [zarr-indexing](https://zarr.readthedocs.io/projects/zarr-indexing/en/latest/), in the
  zarr-python repository, separates a zero-based positional dialect from an absolute index domain
  and works through negative-origin domains and prependable grids in its design notes.
- The [rectilinear chunk grid](https://github.com/zarr-developers/zarr-extensions/tree/main/chunk-grids/rectilinear),
  descended from ZEP 3, varies the chunk length along a dimension and does not define negative
  grid indices. Under the `offset` wrapper grid (zarr-extensions#81) its chunk 0 can be placed at
  the array's lower bound, so that an array with `bounds` needs none.
- [OME-NGFF](https://ngff.openmicroscopy.org/specifications/dev/#coordinate-convention) defines the
  index space of an array as zero-based from its first element and places it with a `translation`
  per level. After a prepend that `translation` points at a different element, so a writer updates
  it by the amount grown; the existing elements do not move.

## Implementation

Three prototypes exist. Each reads the metadata at one site and normalises it to a lower bound, a
shape and a grid origin there; everything downstream is one path. They were first written against
the chunk grid form of this design and moved to `bounds` and the `offset` grid by changes
concentrated at that site in each, so any of the forms discussed under Alternatives costs about the
same downstream.

- zarr-python [#4516](https://github.com/zarr-developers/zarr-python/pull/4516): `Array.prepend`
  and `Array.domain`; indexers offset by the first element's position in its chunk.
- tensorstore [#296](https://github.com/google/tensorstore/pull/296): bounds as the index domain,
  resizing of the lower bound, negative components in key range listing.
- neuroglancer [#1133](https://github.com/google/neuroglancer/pull/1133): read support, chunk space
  relative to the grid origin.

Steps:

1. A zarr-specs pull request with the changes described here: core specification (`bounds`,
   derived shape, example, resizing note), regular chunk grid (negative indices, partial first
   chunk), `default` and `v2` chunk key encodings (sign, `-0`). The sharding codec specification
   is not changed; its "array shape" is read as the array's bounds.
2. The `offset` chunk grid in zarr-extensions (zarr-extensions#81): a wrapper that places any
   grid's chunk 0 at a chosen coordinate. It needs no specification change and is registered
   independently of this ZEP; the two are complementary.
3. The three prototypes read `bounds` and the `offset` grid.

## Alternatives

- **A chunk grid extension** (the first draft of zarr-extensions#81: `chunk_shape`, `origin`,
  `lower_bound` in the grid configuration). Needs no specification change, and every reader
  checked (zarr-python, tensorstore, neuroglancer) refuses an unknown grid name. Not chosen for the
  reason given under Motivation: the array's extent would live inside the chunk grid.
- **A top-level `origin` beside `shape`** ([@normanrz](https://github.com/normanrz) on
  zarr-extensions#79): the lower bound is `origin`, the upper is `origin + shape`, and an absent
  `origin` means zeros. One definition of the extent, so no second code path, and it serves positive
  origins as well. Its safety rests on the core rule that a reader fails on an unrecognised member,
  which neuroglancer does not apply (table under Backward Compatibility), whereas `bounds` is
  refused by every reader checked. The name would also collide with the chunk grid's `origin`. The
  working group has not chosen between the two forms; this ZEP
  proposes `bounds` for the refusal guarantee and switches if the group prefers a single
  definition of the extent.
- **`origin` on the `regular` chunk grid** (earlier drafts of this ZEP): an optional member of the
  `regular` configuration giving the coordinate at which chunk 0 begins, permitted only beside
  `bounds` because some readers ignore an unknown member of that configuration (table under
  Backward Compatibility). Dropped in favour of the wrapper grid suggested by
  [@LDeakin](https://github.com/LDeakin) on zeps#72: a registered grid, `offset`, whose
  configuration holds an `offset` and a `base_chunk_grid`, so that any grid gains an origin
  without a member of its own and an unknown grid name is refused by every reader checked. It
  costs more metadata per array and one more level for a reader to parse, and it keeps this ZEP
  to `bounds` and negative grid indices. zarr-extensions#81 carries it.
- **An `offset` chunk key encoding** (zarr-extensions#80), shifting the key numbering by a stored
  offset. Withdrawn on review: tied to one encoding, worse key ordering, shifted logical
  coordinates, and no growth by part of a chunk.
- **Per-dimension pairs,** `[[start, stop], ...]`, or two top-level members `lower_bound` and
  `upper_bound`, instead of an object. The first draft used pairs. The object was taken on review
  ([@normanrz](https://github.com/normanrz) on zeps#72): its member names state the half-open
  convention in the metadata itself, and `inclusive_min`/`exclusive_max` is how tensorstore already
  spells an index domain in JSON, so one existing parser reads it.
- **A store-level shift,** as in Icechunk. Only in that store, and only by whole chunks.
